## 2. `runtime.MemStats`

历史上我把 `MemStats.Sys` 近似理解成了 `top` 里的 RSS，这个理解不准确。

需要区分三件事：

1. **RSS**：操作系统视角下，当前进程实际驻留在物理内存中的页。
2. **`runtime.MemStats.Sys`**：Go runtime 从操作系统获得/保留的虚拟地址空间总量，是各类 `XxxSys` 字段之和。
3. **Go runtime 当前尝试约束的内存量**：软内存上限使用的近似量是 `MemStats.Sys - MemStats.HeapReleased`。

因此：

```text
Sys != RSS
Sys != HeapSys + StackSys
```

`Sys` 还包括 GC 元数据、mspan、mcache、profiling 等 runtime 自身结构。

### 2.1. 堆相关字段

```text
HeapAlloc
    当前已分配给堆对象的字节数。

HeapSys
    runtime 为堆保留的地址空间。

HeapInuse
    当前用于 span 的堆内存。

HeapIdle
    当前处于 idle span 的堆内存。

HeapReleased
    已经归还给底层系统的 idle 内存。
```

可以把下面这两个关系作为理解入口：

```text
HeapSys = HeapInuse + HeapIdle

HeapIdle - HeapReleased
    ≈ runtime 仍保留、目前未使用且尚未归还给 OS 的堆内存
```

### 2.2. 栈与 runtime 元数据

当前 `MemStats` 中比较重要的还有：

```text
StackInuse
StackSys
MSpanInuse / MSpanSys
MCacheInuse / MCacheSys
GCSys
OtherSys
```

所以不能只看 Heap 和 Stack 两类就解释整个 `Sys`。

### 2.3. GC 相关字段

```text
NextGC
LastGC
PauseTotalNs
PauseNs
NumGC
NumForcedGC
GCCPUFraction
```

例如：

```text
GCCPUFraction = 0.03
```

表示自程序启动以来，GC 消耗的可用 CPU 时间比例约为 3%。

## 3. `runtime/metrics`

现在如果要做监控，更推荐同时了解 `runtime/metrics`。它提供了比 `runtime.ReadMemStats` 更通用、可扩展的 runtime 指标接口。

内存相关指标常见的有：

```text
/memory/classes/total:bytes
/memory/classes/heap/objects:bytes
/memory/classes/heap/free:bytes
/memory/classes/heap/released:bytes
/memory/classes/heap/stacks:bytes
/memory/classes/metadata/mcache/inuse:bytes
/memory/classes/metadata/mspan/inuse:bytes
```

其中：

```text
/memory/classes/total:bytes
  - /memory/classes/heap/released:bytes
```

与 `MemStats.Sys - MemStats.HeapReleased` 表达的是同一个 Go runtime 软内存上限口径。

## 4. 和 RSS 的关系

如果目标是解释“为什么 Go 进程 RSS 很高”，不能只看 `MemStats.Sys`。

还要考虑：

- runtime 已经 release 但地址仍映射的页；
- cgo/C 分配；
- `syscall.Mmap` 等 runtime 之外的映射；
- OS thread stack；
- 文件映射、共享页以及操作系统统计口径。

所以排查时应把 **runtime 指标 + OS 指标** 一起看。
