## 1. 逃逸分析
Go 中变量最终放在栈还是堆上，不由 `new`、`make` 或“返回指针”这类语法直接决定，而由编译器根据变量的生命周期、引用关系、调用边界以及当时版本的优化能力判断。

因此，同一段源码在不同 Go 版本中，逃逸结果可能发生变化。

## 2. 为什么需要逃逸分析

|     | 堆 | 栈 |
| --- | --- | --- |
| 回收 | 由 GC 管理 | 随栈帧生命周期管理 |
| 分配成本 | 通常更高 | 通常更低 |

逃逸分析的目标之一，就是在保证语义正确的前提下，让更多对象留在栈上，减少堆分配和 GC 压力。

## 3. 如何观察逃逸分析

不要把逃逸规则总结成“函数外有引用就一定逃逸”这种固定口诀。编译器的分析规则比较复杂，并且会持续演进，最可靠的方法是直接查看当前编译器输出。

```bash
go build -gcflags=-m=3 .
```

如果需要观察所有依赖包，可以按需要使用：

```bash
go build -gcflags=all=-m=2 .
```

输出中的 `escapes to heap`、`moved to heap`、`does not escape` 等信息可以帮助定位具体原因。

## 4. 例子

```go
package main

import "fmt"

func foo() *int {
	t := 3
	return &t
}

func main() {
	x := foo()
	fmt.Println(*x)
}
```

这类例子经常用于说明“返回局部变量地址”并不会产生悬垂指针：如果变量必须在函数返回后继续存活，编译器会安排它逃逸到堆上。

历史版本中可能看到类似：

```text
moved to heap: t
```

但具体诊断文本、是否内联、`fmt.Println` 参数是否逃逸，都可能随着编译器优化发生变化，不应该把某一次输出当成语言规范。

如果想确认最终是否出现堆分配，还可以结合汇编输出：

```bash
go build -gcflags=-S .
```

历史版本里看到 `runtime.newobject` 往往说明出现了堆对象分配，但这个实现细节同样不保证跨版本稳定。

## 5. 当前版本补充

- Go 编译器一直在提高逃逸分析和栈上分配能力。
- Go 1.26 又扩大了部分 slice backing store 的栈分配场景。
- 优化代码时，优先通过 benchmark、pprof 和编译器诊断确认“这次逃逸是否真的构成瓶颈”，不要为了让某个变量留在栈上而牺牲代码可读性。
