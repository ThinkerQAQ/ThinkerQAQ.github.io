## 1. Runtime Data Areas

The JVM specification defines several logical runtime areas. Commonly discussed ones are the heap, per-thread Java stacks, the method area, program counters, and native-method stacks.

These are **specification concepts**. Their physical layout and memory-management implementation depend on the JVM.

## 2. Heap

The heap stores ordinary Java objects and arrays and is shared by threads. It is the main region managed by the garbage collector.

Generational regions such as young/old generation are collector/implementation choices rather than a universal JVM specification requirement.

## 3. Java Stack

Each platform thread has execution-stack state composed of frames. A frame contains local variables, operand-stack state, and bookkeeping for the current method invocation.

Deep recursion can exhaust stack space and produce `StackOverflowError`.

## 4. Method Metadata

Class metadata, runtime constant-pool data, method metadata, and related structures conceptually belong to the method-area role. In HotSpot, modern JDKs store much class metadata in **Metaspace**, which uses native memory rather than the old PermGen design.

## 5. Program Counter and Native State

Each executing thread needs state identifying where execution should continue. Native calls also involve implementation-specific native stack/state.

When diagnosing memory problems, distinguish Java heap, class metadata, thread stacks, direct/native buffers, code cache, GC structures, and other native allocations rather than calling all process memory “heap”.
