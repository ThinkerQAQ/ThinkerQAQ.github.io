## 1. Why a Pool?

A thread pool separates task submission from execution and bounds/reuses platform-thread resources.

The main system-design value is not only avoiding thread-creation cost—it is controlling **concurrency and queueing**.

## 2. `execute` Policy

Simplified `ThreadPoolExecutor` flow:

1. if workers < `corePoolSize`, create a worker;
2. otherwise try to enqueue;
3. if the queue rejects/full and workers < `maximumPoolSize`, create another worker;
4. otherwise invoke the rejection handler.

Queue type therefore fundamentally changes pool behavior.

## 3. Important Parameters

- `corePoolSize`;
- `maximumPoolSize`;
- work queue;
- keep-alive time;
- thread factory;
- rejection policy.

Use named threads and an uncaught-exception/observability strategy.

## 4. Bound the Queue

An unbounded queue can keep accepting work long after throughput capacity is exceeded. Latency and memory then grow until the service fails elsewhere.

Prefer a queue/concurrency bound derived from acceptable latency and downstream capacity.

## 5. Rejection Is Backpressure

Rejection is not merely an exception to suppress. It is the point where the executor says its bounded capacity is exhausted.

Possible policies include reject, caller-runs, drop, or custom load shedding—each changes system semantics.

## 6. Sizing

For CPU-bound tasks, useful platform-thread concurrency is often near available CPU parallelism. For blocking I/O it can be higher, but Little's Law and downstream capacity should drive the limit rather than one formula.

## 7. Virtual Threads

Modern Java virtual threads change the cost model for blocking-per-request concurrency. They reduce the need to pool threads merely because platform threads are expensive.

They do **not** remove the need to limit scarce downstream resources such as DB connections, rate-limited APIs, or memory.
