## 1. What It Provides

`ReentrantLock` provides reentrant mutual exclusion with capabilities beyond intrinsic `synchronized` syntax:

- `tryLock()`;
- timed lock acquisition;
- interruptible acquisition;
- optional fairness policy;
- multiple `Condition` queues.

## 2. Correct Usage

```java
lock.lock();
try {
    // protected invariant
} finally {
    lock.unlock();
}
```

Always release in `finally`.

## 3. Reentrancy

The owning thread may acquire the lock repeatedly; an internal hold count tracks nested acquisitions. It must release the same number of times.

## 4. Fairness

A fair lock generally favors long-waiting threads, reducing barging at the cost of throughput/latency overhead. Nonfair mode is the default and often has better throughput.

Fairness is not a strict real-time scheduler guarantee.

## 5. `synchronized` vs. ReentrantLock

Choose based on API needs and clarity, not an old rule that one is 'light' and the other 'heavy.' Modern JVMs optimize both.
