## 1. What `synchronized` Guarantees

`synchronized` provides mutual exclusion around a monitor plus Java Memory Model ordering/visibility guarantees.

An unlock of a monitor happens-before a later successful lock of the same monitor. Therefore writes performed before leaving the synchronized region are visible to code that subsequently acquires that monitor.

## 2. Lock Object

### Instance Method

```java
synchronized void f() { ... }
```

Locks `this`.

### Static Method

```java
static synchronized void f() { ... }
```

Locks the corresponding `Class` object.

### Block

```java
synchronized (lock) {
    // critical section
}
```

Locks the explicit monitor object.

Correctness depends on every participant using the same lock for the same invariant.

## 3. Reentrancy

Java intrinsic monitors are reentrant: a thread that already owns the monitor can enter synchronized code guarded by the same monitor again.

## 4. Bytecode

Synchronized blocks use monitor-enter/exit semantics (`monitorenter`/`monitorexit` bytecodes). Synchronized methods encode synchronization in method metadata and the JVM applies equivalent monitor behavior.

## 5. Not Inherently 'Heavyweight'

It is outdated to classify `synchronized` itself as always a heavyweight OS lock. Modern JVMs optimize uncontended and contended monitors using implementation techniques that change over JVM releases.

What is stable is the language contract: mutual exclusion, reentrancy, and happens-before.

## 6. Use It When

Use a monitor when multiple operations over shared mutable state form one invariant that must be protected as a critical section.

For a single counter or reference update, an atomic variable may express the intent more directly; for richer lock capabilities, `ReentrantLock` may be appropriate.
