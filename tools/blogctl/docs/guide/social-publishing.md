# Social Publishing via Buffer

BlogCTL supports social posts independently of long-form article syndication. The AI writes
the actual English copy; BlogCTL validates an existing canonical source, adds a tracked
URL, retains local review state, and publishes through Buffer only after explicit approval.

## Architecture

```text
ChatGPT / local AI agent
    -> structured DraftInput JSON
    -> blogctl social create
    -> BlogCTL Web Console / Social tab
    -> review + optional edits + explicit approval
    -> Buffer private draft (stage)
    -> explicit public publish
```

There is no embedded LLM, web-facing AI service, or browser-cookie based LinkedIn adapter.
X and Bluesky become available only after connecting those channels in Buffer.

## Configuration

BlogCTL uses its existing local **blogctl.toml** file, not YAML:

```toml
[social.buffer]
api_key = "YOUR_PERSONAL_BUFFER_API_KEY"
```

On Linux, this normally lives at `~/.config/BlogCTL/blogctl.toml`. On Windows
it is stored in the installed executable's `Data/blogctl.toml`. You can also edit
the key under **Settings → Distribution platforms → Buffer API** in the BlogCTL
Web Console. Key values are masked in API responses and are never logged.

The `BUFFER_API_KEY` environment variable is supported as a fallback when
`api_key` is absent, but an interactive Bash variable in `.bashrc` is not
necessarily visible to noninteractive/Windows Bridge processes.

**Critical on Windows + WSL**: the CLI process and Web Console must share the
same BlogCTL Data directory. Point `BLOGCTL_DATA_DIR` in WSL to the actual
mounted Windows `Data` directory, or execute BlogCTL with the same configured
Data directory on both sides. This path must be absolute and accessible from
the process. Do **not** use separate Linux/Windows default data directories
if you expect immediate cross-surface draft previews.

Never commit a real API key, `blogctl.toml`, or `Data/social/*.json`.

## Draft input contract

The AI outputs **only** the social expression: no publication IDs, invented
canonical URLs, credentials, or API calls.

```json
{
  "id": "mutex-memory-guarantees",
  "source": {
    "kind": "article",
    "slug": "concurrency-series-03-mutex",
    "language": "en"
  },
  "posts": {
    "linkedin": {
      "text": "A mutex is more than mutual exclusion. ...",
      "mediaUrl": "https://public-example.invalid/article-cover.jpg"
    }
  }
}
```

Remove `mediaUrl` for a text-only post; use a publicly accessible HTTPS image
for an image post. Set `linkCard: true` without `mediaUrl` to use the
LinkedIn link attachment mechanism. Images and link cards are mutually exclusive.

`source.kind` supports `article`, `series`, and `project`. The source
must exist in the configured BlogContent checkout with an English version.
Canonical URLs and tracking parameters are generated by BlogCTL.
The input text should **not** contain the article URL, as it is appended by
the deterministic renderer.

## CLI

From the blog engine checkout, using the intended shared Data directory:

```bash
blogctl social channels
blogctl social source --kind article --slug concurrency-series-03-mutex \
  --content-root /path/to/BlogContent
blogctl social create --input /tmp/mutex-social.json \
  --content-root /path/to/BlogContent
blogctl social list
blogctl social show --id mutex-memory-guarantees
```

Review the `revision` from `show`, or edit and approve the current content
in the **Social** Web Console tab.

```bash
blogctl social approve --id mutex-memory-guarantees --revision <reviewed-revision>
blogctl social stage --id mutex-memory-guarantees --platform linkedin \
  --revision <reviewed-revision>
```

`stage` creates a **private Buffer draft**, not a public LinkedIn post. The
user must explicitly confirm any publication:

```bash
blogctl social publish --id mutex-memory-guarantees --platform linkedin \
  --revision <reviewed-revision>
```

`publish` only advances an already-staged, verified remote draft. It never
creates a new post as a fallback. A network timeout or unexpected remote state
is recorded as unresolved to prevent duplicate retries; verify the outcome in
Buffer before any manual recovery. Text edits invalidate the approved revision
and cannot silently replace an already-staged Buffer draft.

**Current limitations:** no automatic AI summarization inside BlogCTL, no
background scheduling UI, and no automatic reconciliation after ambiguous
Buffer writes. All remote writes require explicit actions.
